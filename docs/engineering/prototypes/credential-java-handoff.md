# Isolated credential migration experiment — handoff

Status: **prototype only; not ready to integrate, deploy, or operate on real credentials**. An archival copy of the Java sources is stored under [credential-java](credential-java/README.md) as `.java.txt` for review; it is outside application source directories and is not compiled. None of the prototype runtime classes are integrated into the application. The fake codec deliberately used by Linux tests is reversible and does not protect secrets.

## What the experiment explores

- `src/main/java/com/vncode/app/shared/credential/PrototypeCredential{Codec,Access,Reader,Writer,MigrationService}.java`: an explicit per-field format, legacy prefix treated as data, protection and round-trip validation before acquiring a write lock, source recheck in the transaction, atomic SQL updates and metadata, and fail-closed reads. The prototype contains a test injection hook and **must not be shipped as-is**.
- Synthetic shop/consumer experiments: `PrototypeShopSecrets`, the adapted `ShopRepository`, `ListingIdentity`, `KizService`, `KizWarehouseRepository`, `ListingCopyService`, `ProductRepository`, `OzonProductGtinMappingRepository`, and `OzonCardRegistrationRepository`. The experimental changes appear only as inert `.java.txt` archival copies under `credential-java`; they do not cover all production behavior and must not be copied individually.
- Java tests: `PrototypeMigrationTest`, `PrototypeCredentialConsumerContractTest`, `PrototypeShopConsumerTest`, and `CredentialMigrationGateFixtureTest`. The gate in the latter is test-only and uses the actual snapshot service with synthetic SQLite fixtures. It does not connect the migration to startup.
- `PrototypeWindowsDpapiTest` is archived as source text alongside the experiment. It is a synthetic CurrentUser round-trip, purpose-separation and corrupt-ciphertext test. It has **not been run on Windows** and is not included in the combined result below. Cross-Windows-user, profile loss and recovery tests remain to be designed and executed.

## Verified snapshot

On Linux with JDK 25, a single frozen source copy, now archived under `credential-java` except for the separately noted Windows test, passed **18 tests, zero failures and zero skipped**:

```sh
/workspace/toolchains/mvn-vncode -B \
  -Dtest=PrototypeMigrationTest,PrototypeCredentialConsumerContractTest,PrototypeShopConsumerTest,CredentialMigrationGateFixtureTest test
```

The archived migration-service file has SHA-256 `f61def9d4e8927b2a52ef6e2d80d63db406861242290747a3f1e33d67a67c551`. The result covers fake-codec behavior, including nullable/empty values, a missing OMS JSON field, absence of the lazily created pipeline table, source changes, transactional interruption, rollback, a verified synthetic snapshot, preservation of two historical OMS values, owner/fingerprint behavior, and duplicate credentials. It is **not** a production migration, startup integration, Windows DPAPI, platform compatibility, real seller data, or end-to-end application test.

## Outstanding blockers before any runtime integration

1. **OMS ownership and all read/write paths.** `ZnackRepository.pipelineSettings()` calls `bindPipelineConnections()` even on a read, which may write a profile. Protecting only reads can reintroduce plaintext. When a profile row is missing, the existing schema cannot distinguish a truly unbound legacy pipeline from a formerly bound profile that was lost; the current code can bind the latter to the shop's newer OMS. Never infer ownership or silently use the current OMS for an ambiguous old pipeline. The experiment does not solve this. `ZnackSchemaSupport` may retain unscoped legacy OMS data as well.
2. **Transaction compatibility.** The prototype writer insists on JDBC `getAutoCommit()==false`; existing `SqliteWriteTransaction` issues `BEGIN IMMEDIATE` manually while JDBC still reports autocommit true. Do not remove the guard without a proven transaction primitive, rollback tests, and preserved immediate-lock semantics. Writes to values and their format metadata must commit or roll back together.
3. **Startup and recovery.** `LocalDataMigrationGate` can skip `Database.initDatabase` when its ready marker is valid; another code path invokes initialization directly. The real startup must detect the migration state before consumers run, hold the application-data lock, create and verify a snapshot, and ensure interruption recovery and rollback are explicit and tested. Current snapshot creation alone does not automatically restore after an initialization failure. Protect against older binaries interpreting encrypted values as plaintext.
4. **Metadata lifecycle and JSON representation.** Delete/rotation of shops, settings and pipelines needs atomic metadata maintenance without deleting business history; polymorphic metadata currently lacks foreign keys and can become orphaned. For a missing OMS JSON attribute, runtime readers must distinguish attribute absence from explicit JSON null using the original JSON, not merely a Java null. Recheck ownership, scope and protected value at every use of any short-lived cache; include rotation during a running batch.
5. **Platform and credentials.** Run actual DPAPI CurrentUser tests on Windows using synthetic secrets and separate test profiles, including process restart, changed Windows user, lost key, tampering, incorrect purpose, oversized/unicode data, error reporting and snapshot restore. Confirm an explicit supported-platform policy for non-Windows; do not silently fall back to plaintext or block the entire application without an agreed design. No API keys, OMS secrets, licenses, or production databases should be used in CI.
6. **Audit and data retention.** Snapshot files, SQLite WAL/free pages, and legacy tables can retain plaintext from before migration. The prototype does not establish secure erasure or appropriate ACLs. Do not delete recovery copies or claim that existing plaintext is removed. Ensure UI and error/reporting paths do not expose credentials.
7. **Full integration and regression.** Exercise all consumers, purchase/recovery pipelines, signer identity, legacy import, duplicate seller tokens, old and new binary compatibility, interrupted writes, large stores and DPAPI process count. A DPAPI PowerShell process per row/identity check can cause severe slowdown; a cache requires scoped lifetime, source/revision revalidation and invalidation tests. Review all error handlers that might suppress decryption failures as empty mappings.

The archival `.java.txt` files and test documentation are review material only; they do not participate in the build. Do not integrate the experimental runtime changes until the blockers above are resolved together and tested on Windows and Linux.
