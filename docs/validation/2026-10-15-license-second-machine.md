# Second-machine license timeout: 1.4.10

Owner confirms 1.4.9 on a second Windows computer connected through a mobile hotspot still reports `LICENSE_TIMEOUT`, despite a two-device entitlement. Earlier curl configuration/status probes do not prove connectivity from the Java runtime or successful authenticated POST activation on that machine. The requested credential-free POST probe on the second machine has not yet been returned. No real key is requested or sent by support probes.

The Portal device limit already supports the same key on two independent device identities. Version 1.4.10 adds an explicit compatible license transport: HTTP/1.1 with IPv4-first system DNS results, retaining IPv6 fallback and IPv6-only networks. Default Automatic behavior remains available. The preference contains only an enum and is saved atomically in `license-network-mode.txt` in the app data directory, independently of the protected device/license state. Saving failures retain the prior transport. Neither mode changes the HTTPS origin, proxy policy, trust manager, device proof, server signature, offline boundaries or one-shot POST behavior.

The License screen adds connection checking and copyable results, available before Gmail registration or activation. Probes compare Automatic and Compatible using the actual clients, GET public configuration and POST `{}` without authorization to the activation route. The expected POST result is 401 `AUTH_REQUIRED`, which occurs before device allocation, signing or license redemption. Reports contain only fixed endpoint/profile names, HTTP status/protocol, elapsed milliseconds and sanitized failure phase/code. They exclude server response bodies, proxy addresses, IPs, tokens, Gmail, keys and device signatures. Redirects remain disabled. Per-call probe budgets are 10 seconds total, 4 seconds connect and 6 seconds read/write; operating-system DNS/proxy behavior can still delay cancellation.

Support operations use the existing bounded license worker. Failures never pass through license denial handling; checks/mode changes cannot replace or invalidate an existing lease. Generation cancellation completes queued support futures, and disposed views drop late results. Activation feedback remains directly after the activation card. Network controls are below it and reports stay hidden until a check completes.

Local checks: 81 Java/JavaFX tests passed, 0 failures/errors/skips; 53 release-contract tests passed. Coverage includes actual TLS negotiation (HTTP/2 Automatic vs HTTP/1.1 Compatible), rejection of untrusted certificates in both profiles, DNS privacy, response timeouts, no redirects, IPv6 retention, preference persistence/failure, no credentials in probes/clipboard, unregistered UI access, async/dispose/cancel handling and unchanged active license/device state.

The real Worker → in-memory D1-compatible adapter → HTTP → Java service/verifier contract additionally activates the same issued key on a second independent device in Compatible mode, renews it without adding days, and denies a third device at the two-device limit. The test uses fixture credentials/issuer keys; it is not production carrier or multi-device acceptance. The 1.4.8 update handoff regression remains covered.

Windows/native, artifact and public download bindings are recorded in the 1.4.10 release record after CI. Actual activation on the affected second machine remains unverified until the owner installs the build, enables Compatible mode and retries. A diagnostic report is required if it still fails; no root cause on that machine is asserted from passing fixture tests.
