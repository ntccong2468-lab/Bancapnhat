# Catalog allocation: shared pool and restart recovery

- WB and Ozon use the same durable allocation journal pool scoped to the National Catalog participant and environment. A pending or unknown allocation blocks a second allocation in the same pool across shops, certificates, processes and app restarts. Legacy native `ALLOCATING_GTIN` / unknown checkpoints are checked before dispatch; malformed legacy ownership fails closed.
- Ozon persists a generation with each new reviewed allocation claim. A crash after a confirmed journal ACK but before its native GTIN checkpoint can recover the exact receipt only when owner, certificate, environment, product, generation, approved payload and freshly read product/schema revisions still match. The journal read and native checkpoint update are one SQLite transaction. Missing/unknown ACK, old records without a generation and changed source data are not replayed. Recovery does not invent signing or marketplace consent.
- Targeted mock/SQLite checks passed for two marketplaces, legacy unknown outcomes, process restart, two concurrent JVM processes, changed source/schema/certificate/generation, missing payload and restart before submission. No real allocation, seller write or live Catalog registration was performed.
- The shared allocation journal applies the existing documented production contract guard to Ozon. Ozon sandbox GTIN allocation that previously could reach the API is now stopped with `V3_SANDBOX_AUTH_UNVERIFIED`; the Ozon sandbox test confirms zero allocation and submission requests. This is a compatibility restriction, not evidence of sandbox support.
- This allocation guard alone does not prove deduplication of every already-existing GTIN across the two marketplaces. A separate submission guard and its material owner-evidence limitation are described in `2026-10-30-cross-market-catalog-submission.md`; no live cross-market write was verified.
